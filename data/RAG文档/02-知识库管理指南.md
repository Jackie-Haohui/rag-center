# 02 - 知识库管理指南

> **Knowledge Base Management**  
> 知识库是 RAG 系统中组织和隔离文档的核心容器。理解知识库的创建、配置、版本管理是高效使用 rag-center 的基础。

---

## 1. 知识库的核心概念

### 1.1 什么是知识库？

知识库（Knowledge Base）是一组文档的逻辑集合。你可以按领域、项目、部门等维度创建不同的知识库：

```
Tenant: "公司A"
  ├── KB: "员工手册"        → 50篇文档
  ├── KB: "技术规范"        → 200篇文档
  ├── KB: "客服FAQ"         → 500篇文档
  └── KB: "合规法规"        → 100篇文档
```

### 1.2 数据模型

```python
# app/models/knowledge_base.py
class KnowledgeBase(Base):
    __tablename__ = "knowledge_bases"

    id: str              # UUID, 唯一标识
    tenant_id: str       # 归属租户 (多租户隔离)
    name: str            # 知识库名称
    description: str     # 描述 (用于LLM理解知识库领域)
    settings: dict       # JSONB, 灵活配置 (如同义词表)
    active_index_version: str  # 当前激活的索引版本 "v1"/"v2"
    created_at: datetime
    updated_at: datetime
```

## 2. 创建知识库

### API 调用

```bash
POST /api/v1/knowledge-bases/create
Authorization: Bearer <your_api_key>
Content-Type: application/json

{
    "name": "产品手册",
    "description": "包含所有产品线的使用手册、规格参数和常见问题"
}
```

### 关键限制（按套餐）

| 套餐 | 最大KB数 | 每KB最大文档数 |
|------|:-------:|:-----------:|
| Free | 1 | 30 |
| Standard | 5 | 200 |
| Pro | 50 | 5,000 |

### 后端创建流程

```python
# app/services/knowledge_base_service.py
def create(self, tenant_id, request):
    # 1. 检查配额
    QuotaService.check_create_kb(tenant_id)

    # 2. 创建KB记录
    kb = KnowledgeBase(id=uuid, tenant_id=tenant_id, name=..., settings={})

    # 3. 创建初始索引版本
    IndexVersionService.create_initial(tenant_id, kb_id=kb.id)
    #    默认版本: "v2", 状态: "active"

    # 4. 提交并返回
    db.commit()
```

## 3. 知识库设置 (Settings)

知识库的 `settings` 字段是一个灵活的 JSONB 配置，当前支持：

### 3.1 同义词扩展

在知识库设置中配置同义词组，检索时自动展开：

```json
{
    "synonyms": [
        {
            "terms": ["退款", "退货"],
            "expand": ["退换货", "退款流程", "金额返还"]
        },
        {
            "terms": ["加班", "OT"],
            "expand": ["加班费", "加班申请", "调休"]
        }
    ]
}
```

**工作流程**：
```
用户输入："怎么申请加班"
    │
    ▼ 匹配到 terms: ["加班", "OT"]
    │
    ▼ 自动追加: "加班费 加班申请 调休"
    │
    ▼ 最终检索串: "怎么申请加班 加班费 加班申请 调休"
```

### 3.2 设置更新 API

```bash
PATCH /api/v1/knowledge-bases/{kb_id}
Content-Type: application/json

{
    "settings": {
        "synonyms": [...]
    }
}
```

## 5. 索引版本管理 🔥

rag-center 支持**多版本索引并存**，你可以在不中断服务的情况下重建索引。

### 5.1 版本状态流转

```
building → ready → active → archived
              │                 │
              ├─────────────────┘ (跳过active直接归档)
              │
           failed (构建失败)
```

### 5.2 版本管理 API

```bash
# 查看所有版本
GET /api/v1/knowledge-bases/{kb_id}/index-versions

# 触发重建 (创建新的 building 版本，异步执行)
POST /api/v1/knowledge-bases/{kb_id}/index-versions/rebuild

# 激活指定版本 (切换检索使用的版本)
POST /api/v1/knowledge-bases/{kb_id}/index-versions/{version}/activate

# 删除指定版本
DELETE /api/v1/knowledge-bases/{kb_id}/index-versions/{version}
```

### 5.3 v1 vs v2 对比

| 特性 | v1 (LEGACY) | v2 (DEFAULT) |
|------|:-----------:|:-----------:|
| 分块方式 | 简单字符切割 | 结构化标题切割 |
| 检索文本 | 直接用 content | 增强的 retrieval_text |
| 章节标识 | ❌ | section_id (稳定UUID) |
| 父级关系 | ❌ | parent_section_id |
| 顺序索引 | ❌ | order_index |
| 引用图 | ❌ | chunk_relations |
| 图注入 | ❌ | ✅ |
| 上下文扩展 | ❌ | ✅ (前后块/父章节/引用) |

## 6. 删除知识库

```bash
DELETE /api/v1/knowledge-bases/{kb_id}
```

**注意事项**：
- 删除前会检查是否有文档正在索引中（PROCESSING 状态）
- 如果有文档正在处理，会返回错误要求等待
- 删除是级联的：KB → Documents → Chunks → Relations
- **操作不可逆，请谨慎使用**

## 7. 最佳实践

### 7.1 知识库划分建议

| 场景 | 建议 |
|------|------|
| 单一领域 | 1个KB, 按文档类型分文件夹 |
| 多部门 | 1个部门1个KB, 联合检索时传 kb_ids |
| 多语言 | 同语言放同一KB, 或混合同一KB |
| 版本迭代 | 使用 index-version 而非新建KB |

### 7.2 描述字段的价值

知识库的 `description` 字段会被传入 LLM（用于 Query Rewrite 和 Research），写好它很重要：

```
✅ 好的描述:
"公司内部的人力资源政策与流程文档，包含考勤、请假、加班、薪酬、绩效评估等内容"

❌ 差的描述:
"HR文档" 或空
```

### 7.3 索引版本策略

```
日常使用:    保持 active 指向 v2 (最新最佳质量)
灰度验证:    rebuild → ready → 小流量验证 → activate
回滚方案:    保留上一版本 (archived), 可随时 activate 切回
```
